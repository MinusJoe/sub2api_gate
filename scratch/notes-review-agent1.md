## 1. 三份笔记有无实质矛盾？采信哪些 / 异议哪些

**结论：没有「一方说 X、另一方说非 X」的硬矛盾；只有一处口径需统一 + 若干互补。** 三角是从「获取 → 使用 → 有效性」三个环节，层层递进，且角 3 揭示了一个更深的结论。

**需要统一口径的点（唯一接近矛盾的）**：上一轮「拿票必须走 WS」的误读。
- 角 1 明确纠正：票在 **HTTP 响应头下发**（142/347、恒 780），`sse/responses.rs`(`0x3d135c0`) 有读票点；「WS only」只适用于**回带**。
- 角 2/角 3 都仍写「客户端只在下一次 WS 握手回带，HTTP/SSE 无回带点」，并把它当二手采信（角 2 §5.1 引 notes-binary §2.4）。
- 判定：**两边都对，但角 2/角 3 没把「获取」和「回带」分开说**，容易让人误以为「拿票也要 WS」。最终口径必须统一为：**「获取可走 HTTP 响应头；回带仅走 WS 握手」**。这不是矛盾，是表述粒度差。

**我采信的（对方比我更精确/更深，接受并纳入）**：
1. 角 2 的 **Fernet 判定**（585B = 1版本+8时间戳+16IV+528密文+32HMAC，528=33×16 块）——精确解释了 292/332→780 = 密文块数 10/12→33。比我笔记里只报「780」深一层。
2. 角 2 的 **installation_id = 设备级 UUIDv4（非账号派生）** + turn-metadata **32 字段**（我写「~30」，应以 32 为准）。
3. 角 2 的**三重复用错配**（获取/使用/形态）框架。
4. 角 3 的**降智权威判据 = 流内实际模型**（`response.created.response.model`/`openai-model`），safety-buffering 头是「提示非证明」。
5. 角 3 的 **service_tier = 提速档非质量档**、`responses-lite` 值=`"true"`、routing-hint/residency 都是「指纹非 VIP 票」。

**我的保留/异议**：
- 角 2 §3.4 把 292 判为「无填充 base64url 下不自洽」是**推断**，且它自己承认无法证伪 9/22 历史——我认同「现在=780」为铁证，292/332 可信度低，但提醒别把「292 不自洽」当实锤去反推历史。
- 角 3 的「priority 是否 HTTP/SSE 生效」本身标了「历史结论反转、需本环境自测」——这是诚实的不确定，采信其「必须自测」的结论，不采信任何一个方向的定论。

## 2. 我之前的方案：修正（不坚持、不彻底降级）

我之前最推荐「HTTP 形状对齐（删错 beta / 版本 0.163.0 / 身份+元数据+工具对齐）+ 读响应头拿票」。

读完另两角后**修正**为：

1. **技术上这个方案仍正确，但它解决的是「拿票」，不解决「防降智」**。角 2 说清票的正确用法是「per-turn WS 续传、跨账号剥离」，角 3 说清「票根本治不了降智（降智=服务端路由决定，票只是粘性路由，非质量凭证）」。→ 我的「拿票」方案只有和角 2 的「per-turn WS 续传透传」绑定才闭环，且**必须放弃「打票防降智」这个原目标**。
2. **优先级降级**：打票线从「主方案」降为「可选的路由连续性合规项」；「防降智/降智检测」主线应交给角 3 的「流内模型判据 + 账号运维」。

---

## 3. 最终给 sub4api 的合理方案排序（1~3）

**1. 降智检测判据换成「流内实际模型」+ 账号运维（角 3 主线，最高优先）**
把判据从「票形/票有无」换成 `response.created.response.model`（及 `response.metadata.openai-model`）与请求模型比对，并记录 `x-codex-safety-buffering-*`；命中即标记/冷却/换号。可行性高（有检测骨架，只改判据 + 读 SSE/WS body）、风险低-中、成本低-中。**这是唯一真正作用在「质量」上的手段。**

**2. 打票线重构（角 1 形状 + 角 2 用法合并，定位为「合规粘性路由」，不承诺防降智）**
HTTP 形状对齐拿票（删 `OpenAI-Beta: responses=experimental`、版本 0.163.0、originator/UA 与 body 同源、turn-metadata 补 32 字段、加真实 tools）→ 按 per-account/per-turn 只在 WS 握手续传回带 + 跨账号剥离（复用 `guardOpenAICodexTurnStateEcho`）。可行性中、风险中、成本中。

**3. service_tier 当「提速」运营（角 3 次选）**
priority/ultrafast 只当速度档（1.5–8×，计费倍增提前告知），A/B 实测 TPS + `x-codex-primary-used-percent` 消耗速率，不承诺防降智。可行性中（需自测、历史反转）、风险低、成本中。

**一句话总纲**：能治降智的只有「检测+换号/冷却」；打票线若要保留，只做「合规 per-turn 粘性路由」，且必须从「全站共享注入 HTTP」改成「per-turn WS 续传 + 跨账号剥离」。
